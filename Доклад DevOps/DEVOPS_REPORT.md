## Введение

DevOps — это подход к разработке и эксплуатации программного обеспечения, который помогает командам быстрее и надёжнее выпускать изменения. Название объединяет разработку (Development) и эксплуатацию (Operations). Вместо того чтобы передавать готовый проект администраторам «через стену», участники вместе автоматизируют сборку, проверку, публикацию и наблюдение за приложением.

Основные идеи DevOps:

- автоматизация повторяющихся операций;
- совместная ответственность за работу приложения;
- частые небольшие изменения;
- контроль версий и воспроизводимые настройки;
- мониторинг и быстрое исправление проблем.

DevOps — не отдельная программа и не только работа системного администратора. Это набор практик и инструментов. Например, Git хранит историю изменений, CI проверяет проект автоматически, а CD помогает доставить проверенную версию пользователям.

## Как сайт становится доступен по домену

Для публикации сайта на собственном сервере нужен сервер, сетевой адрес, домен и веб-сервер. Упрощённо путь запроса выглядит так:

1. Пользователь вводит доменное имя.
2. DNS находит IP-адрес, связанный с этим именем.
3. Браузер соединяется с сервером по IP-адресу.
4. Nginx принимает HTTP/HTTPS-запрос и отдаёт статические файлы либо передаёт запрос внутреннему приложению.

GitHub Pages уже предоставляет хостинг статического сайта и HTTPS. Собственный VPS добавляет практику настройки сервера, SSH, DNS и Nginx, но требует обновлений, защиты и наблюдения за сервером.

## DNS-серверы, зоны и записи

DNS (Domain Name System) — распределённая система имён. Она позволяет использовать запоминающееся доменное имя вместо числового IP-адреса. DNS не является одной общей таблицей: ответ получают через цепочку серверов, а результаты могут временно храниться в кэше.

Доменная зона — часть пространства имён, за которую отвечает определённая конфигурация DNS. Владелец домена обычно управляет записями через панель регистратора или DNS-провайдера. Авторитетные DNS-серверы публикуют записи этой зоны.

| Тип записи | Для чего используется                            | Пример назначения                   |
| ---------- | ------------------------------------------------ | ----------------------------------- |
| `A`        | Связывает имя с IPv4-адресом                     | `site.example → 203.0.113.10`       |
| `AAAA`     | Связывает имя с IPv6-адресом                     | `site.example → 2001:db8::10`       |
| `CNAME`    | Указывает имя-алиас на другое доменное имя       | `www → site.example`                |
| `MX`       | Указывает почтовые серверы домена                | Получение почты для`example`        |
| `TXT`      | Хранит текстовые значения для проверок и политик | Подтверждение владения доменом, SPF |
| `NS`       | Указывает авторитетные DNS-серверы зоны          | Делегирование DNS-провайдеру        |

`TTL` (Time To Live) задаёт, сколько времени DNS-ответ можно хранить в кэше. Поэтому после изменения записи обновление обычно происходит не мгновенно: резолверы могут продолжать использовать прежнее значение до окончания TTL.

Важно: для `CNAME` указывают доменное имя, а не IP-адрес. Запись `A` или `AAAA` указывает адрес соответствующей версии IP.

## Статические IP-адреса

Статический IP — адрес, который остаётся закреплённым за сервером или сетевым интерфейсом. Для публичного сайта это удобно: DNS-запись продолжает вести на один и тот же адрес, а клиенты и сервисы могут стабильно находить сервер.

Динамический IP может меняться, например при переподключении к сети. Если адрес меняется, DNS-запись нужно обновить; для этого иногда применяют Dynamic DNS. У VPS обычно есть публичный адрес, который провайдер позволяет закрепить или зарезервировать. У домашнего подключения наличие постоянного публичного IP зависит от условий интернет-провайдера.

Статический адрес сам по себе не делает сервер доступным из интернета. Нужны корректная маршрутизация, открытые порты в firewall и работающий сервис. Также существуют частные адреса, например `192.168.1.10`, которые используются внутри локальной сети и сами по себе не маршрутизируются из интернета.

## IPv4 и IPv6

IPv4 и IPv6 — версии протокола IP, который доставляет пакеты между устройствами.

| Свойство             | IPv4                                                   | IPv6                                                                |
| -------------------- | ------------------------------------------------------ | ------------------------------------------------------------------- |
| Размер адреса        | 32 бита                                                | 128 бит                                                             |
| Пример записи        | `198.51.100.25`                                        | `2001:db8::25`                                                      |
| Запас адресов        | Ограниченный                                           | Значительно больший                                                 |
| DNS-запись           | `A`                                                    | `AAAA`                                                              |
| Типичная особенность | Часто применяется NAT из-за дефицита публичных адресов | Поддерживает очень большое адресное пространство и автоконфигурацию |

IPv6 создавался как преемник IPv4, в частности для расширения адресного пространства. Эти протоколы не взаимозаменяемы напрямую: сети и серверы могут поддерживать IPv4, IPv6 или оба протокола одновременно. Совместная работа обоих вариантов называется dual stack. Для сайта важно публиковать `AAAA` только если сервер действительно доступен по IPv6.

Примеры локальных команд:

```bash
ip address       # адреса сетевых интерфейсов
ip route         # таблица маршрутов
ping example.com # проверка доступности узла
```

## Базовые команды Ubuntu

В Ubuntu многие административные операции выполняются с помощью `sudo`, которое запускает одну команду с повышенными правами. Перед выполнением команды с `sudo` важно понимать, какие изменения она вносит.

| Команда                       | Назначение                                             |
| ----------------------------- | ------------------------------------------------------ |
| `pwd`                         | Показать текущий каталог                               |
| `ls -la`                      | Показать файлы, включая скрытые                        |
| `cd /var/www`                 | Перейти в каталог                                      |
| `mkdir site`                  | Создать каталог                                        |
| `cp source destination`       | Скопировать файл                                       |
| `mv source destination`       | Переместить или переименовать файл                     |
| `less /var/log/syslog`        | Просмотреть файл постранично                           |
| `grep "error" file.log`       | Найти текст в файле                                    |
| `sudo apt update`             | Обновить список доступных пакетов                      |
| `sudo apt upgrade`            | Установить доступные обновления                        |
| `sudo apt install nginx`      | Установить пакет Nginx                                 |
| `systemctl status nginx`      | Посмотреть состояние службы                            |
| `sudo systemctl reload nginx` | Перечитать конфигурацию службы без полного перезапуска |
| `df -h`                       | Проверить свободное место на дисках                    |
| `free -h`                     | Посмотреть использование памяти                        |
| `journalctl -u nginx`         | Просмотреть журнал службы Nginx                        |
| `ss -tulpn`                   | Посмотреть сетевые порты и процессы                    |

Для диагностики доступности сайта также полезны `curl -I https://example.com` (запрос заголовков HTTP) и `dig example.com` (DNS-запрос, если установлен пакет `dnsutils`).

## SSH и SSH-ключи

SSH (Secure Shell) — зашифрованный протокол для удалённого доступа к компьютерам. На Ubuntu серверную часть обычно предоставляет OpenSSH. Служба `sshd` принимает соединения, а клиент `ssh` используется на компьютере администратора.

Ключевая пара состоит из закрытого и открытого ключа. Закрытый ключ остаётся только у владельца и не отправляется на сервер. Открытый ключ добавляют в файл `~/.ssh/authorized_keys` пользователя на сервере. При подключении сервер проверяет, что клиент владеет соответствующим закрытым ключом. Это позволяет не передавать пароль по сети при каждом входе.

Пример настройки с локального компьютера:

```bash
ssh-keygen -t ed25519 -C "portfolio-server"
ssh-copy-id user@203.0.113.10
ssh user@203.0.113.10
```

`ssh-keygen` создаёт пару ключей; `ssh-copy-id` устанавливает открытый ключ на сервер; `ssh` открывает удалённую сессию. На системах без `ssh-copy-id` содержимое файла `~/.ssh/id_ed25519.pub` можно добавить на сервере в `~/.ssh/authorized_keys`.

Закрытый ключ нельзя публиковать в репозитории или отправлять другим людям. Его можно защитить парольной фразой. Для публичного сервера также следует использовать отдельную учётную запись администратора и firewall. Отключать вход по паролю следует только после проверки, что вход по ключу действительно работает, иначе можно потерять доступ к серверу.

## Nginx и обратный прокси

Nginx — веб-сервер и прокси-сервер. Он может отдавать статические файлы, принимать HTTPS-соединения, направлять запросы по домену или пути и передавать запросы другим сервисам.

Обратный прокси (reverse proxy) стоит перед внутренним приложением. Браузер обращается к Nginx, а Nginx перенаправляет запрос на приложение, например на `127.0.0.1:3000`. Для клиента внутренний адрес приложения не виден. Такой подход позволяет централизовать HTTPS, маршрутизацию, заголовки и доступ к нескольким приложениям.

Пример минимальной конфигурации для приложения на порту `3000`. Имя `site.example` здесь демонстрационное и не является адресом личного сайта:

```nginx
server {
    listen 80;
    server_name site.example www.site.example;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Здесь Nginx слушает HTTP-порт 80 для указанного домена и пересылает запросы локальному приложению. Заголовки передают приложению исходный домен, IP клиента и используемый протокол. В рабочей конфигурации также настраивают HTTPS-сертификат, обычно на порту 443, и открывают необходимые порты в firewall.

После изменения конфигурации её сначала проверяют, затем применяют:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

Команда `nginx -t` проверяет синтаксис и доступность файлов конфигурации. Если проверка не прошла, новую конфигурацию применять не следует.

## Как это связано с публикацией портфолио

Практическая часть задания уже выполнена: моё личное портфолио собрано и размещено на GitHub Pages. При размещении на собственном сервере ту же статическую сборку (`dist`) можно было бы загрузить на VPS. Тогда DNS-записи `A`/`AAAA` направляли бы собственный домен на IP сервера, SSH позволил бы администратору безопасно подключаться, а Nginx мог бы отдавать файлы сайта. Если бы сайт содержал отдельное серверное приложение, Nginx выступал бы для него обратным прокси.

В реальном DevOps-процессе публикацию можно автоматизировать: после отправки изменений в Git система CI проверяет и собирает проект, а затем доставляет сборку на хостинг. Это уменьшает количество ручных действий и помогает выпускать изменения одинаковым способом.

## Заключение

DevOps помогает связать разработку и эксплуатацию в единый управляемый процесс. DNS связывает доменное имя с адресом, статический IP обеспечивает предсказуемую точку подключения, IPv4 и IPv6 обеспечивают сетевую адресацию, Ubuntu даёт инструменты управления сервером, SSH — безопасный удалённый доступ, а Nginx принимает и маршрутизирует веб-запросы. Вместе эти компоненты позволяют разместить сайт на собственном сервере и поддерживать его доступность.
